## Task 1.2: OCR (PaddleOCR in-process, offline), 2026-10-28

**Setup**
- `PaddleOcrProvider : IOcrProvider` (`src/IProfiler.Infrastructure/Ocr/`).
- Libraries: Sdcb.PaddleOCR 3.3.1 + Sdcb.PaddleInference.runtime.win64.mkl 3.3.1.70 + OpenCvSharp4 / OpenCvSharp4.runtime.win
  4.11.0.20250507 (the version Sdcb.PaddleOCR is built against).
- Models: PP-OCRv5 mobile det + English mobile rec, Paddle 3 format, in the repo under `models/` (source and hashes in
  `models/README.md`). They are copied to `<install>\models\` and read through `AppPaths.Models`. No Sdcb "Online" model
  package: a test fails if one is ever added.
- One engine, lazily loaded inside a lock, one call at a time. Pages are downscaled to 1600 px longest side; boxes are
  scaled back to original pixels. Lines below 0.5 confidence are dropped. Region OCR crops the rectangle, adds a 16 px
  white margin, OCRs it, and drops text fragments whose centre lies outside the region.
- Samples: no real scans yet in `samples/spike/`, so `tools/make-ocr-samples.py` generates synthetic "scans" (made-up
  text): an A4 300 dpi LZW TIFF invoice (0.6° skew, noise, blur, faint "COPY" watermark) and an A4 200 dpi JPEG letter
  (Times, JPEG q70). **Re-run on real scans in Task 1.6** (the plan asks for 5 real samples).

**Offline test in Windows Sandbox (networking disabled): blocked.** In the sandbox, the network was confirmed off: ping
failed with "General failure" and DNS had no server. But App Control blocked the unsigned spike exe ("blocked by your
organization's Device Guard policy"). This is the same unsigned-binary block as the Task 0.5 installer (risk R1, code

**Findings**
- **Word boxes:** Sdcb.PaddleOCR gives lines plus per-character text, but **no character positions** (`RecognizedChar.Index`
  is the index in the string). Word boxes are therefore taken from the line's pixels: the n−1 widest ink-free column gaps
  are the spaces. This is not a character-count split. Check it against the searchable PDF in Task 1.5. If it isn't good
  enough, the fallback is to run the recogniser ourselves and keep the CTC time-step positions.
- **Reading order:** sorting lines by Y broke on the 0.6° skew (table columns came out right-to-left). Lines are now
  grouped into rows first.
- **Watermark:** the generated "COPY" watermark (grey 235) wasn't detected at all, so the 0.5 confidence filter wasn't
  exercised here. Re-check it on real scans that have watermarks.
- **Native size:** the publish is 458 MB uncompressed. The largest files are `paddle_inference_c` 89 MB, `mklml` 88 MB,
  `OpenCvSharpExtern` 59 MB, `mkldnn` 46 MB and `phi` 44 MB. Probably unneeded: `opencv_videoio_ffmpeg` (27 MB),
  `onnxruntime` + `paddle2onnx` (11 MB). Trim these in Task 1.6 and measure the installer size there.
- Paddle's native logging writes a few harmless lines to stderr (deprecated-API warning, oneDNN version).

**Patch-code approach**
- **Preferred: the scanner's own patch-code detection through TWAIN** (A6). **Still to be checked on the AD7100 in Task
  1.1** (not on Avision's spec page; look for a patch-code option in the driver, and whether TWAIN reports it per page).
- **Fallback (prototyped):** OpenCV contours → solid bars 0.05–0.30" thick and at least 0.5" long → four bars in a row with
  0.04–0.14" spaces, overlapping extents and no fifth bar next to them → wide/narrow pattern at 0.14". DPI is estimated from
  the page's short side (A4), because OpenCV doesn't expose the TIFF's DPI tag.
- **Orientation risk (confirmed):** the bar order is read left→right (vertical bars) or top→bottom (horizontal bars). A sheet
  fed upside down reads **Patch 1 as Patch 6** and **Patch 3 as Patch T**; a sheet rotated 90° read Patch T as Patch 3.
  Patch 2 and Patch 4 are symmetric and safe. The software check therefore needs the page orientation from Task 1.4 first.
  Otherwise, sites should use only Patch 2 / Patch 4 as separators, or rely on the scanner's hardware detection.

**Findings**
- For 1D symbols ZXing reports only the two ends of the scan line, so the `BarcodeResult.Box` of a Code39/Code128 is a
  1 px high line inside the symbol. QR boxes span the finder patterns. If M3 needs to highlight whole 1D symbols, grow the
  box from the scan line to the bar ends.
- `ImageFile` helper (load via `ImDecode`, clip, crop with margin) is now shared by the OCR, barcode and patch providers.

## Task 1.4: Image ops (deskew, blank page, orientation, rotation as metadata), 2026-10-28

**Setup**
- `OpenCvImageProcessor : IImageProcessor` (`src/IProfiler.Infrastructure/Imaging/`).
  - **Deskew:** projection-profile search on a 1600 px copy (±10°, 0.5° steps then 0.05°); returns the clockwise correction.
  - **White ratio:** ink = pixels darker than 128. A 2% edge band is ignored (scanner edge shadows), and specks smaller
    than ~0.012" square are dropped.
  - **Export render:** crop (original pixels) → deskew → quarter turn, written to a new file. Bilevel pages stay
    bilevel (nearest neighbour). It refuses to write over the original.
- **Review follow-ups:**
  - `Page.DeskewAngle` (`double?`, metadata only, applied on export).
  - `IOcrProvider.DetectOrientationAsync` → `PageOrientation` (stored as `Page.Rotation`).
  - `IPageAnalyzer` / `PageAnalyzer` (Application layer) sets both when a page arrives; registered in `AppHost`.
- **Orientation method:** text detection once. The 8 largest line boxes (each cut to ≤ 8 line-heights wide) are
  recognised as they are and turned 180°; Rotate180 wins if its mean confidence is ≥ 0.10 higher. This is the "0° vs
  180° OCR confidence" check without two full-page OCR passes.
- Test pages: `tools/make-imaging-samples.py` → 300 dpi 1-bit G4 blank page with specks, near-blank page (specks + staple
  + staple shadow + left-edge scanner shadow), the same in grayscale JPEG with paper texture, a sparse page ("Page 2 of
  2" only), the delivery note at 3° skew, and the delivery note upside down.

**Results** (dev PC, Release)

| Page | Skew correction | White ratio → @0.99 | Orientation (upright / 180°) |
|---|---|---|---|
| blank G4 | 0.00 | 1.00000 → **blank** ✅ | none (no text) |
| near-blank G4, staple + shadow + specks | 0.00 | 0.99980 → **blank** ✅ | none (no text) |
| near-blank grayscale JPEG, staple + shadow | 0.00 | 0.99980 → **blank** ✅ | none |
| delivery note G4 (0.5° generated) | **0.50** ✅ | 0.96957 → content ✅ | upright (0.87 / 0.42) ✅ |
| delivery note G4 (3.0° generated) | **2.95** ✅ | 0.96951 → content ✅ | upright (0.87 / 0.42) ✅ |
| delivery note G4, **upside down** | **0.50** ✅ | 0.96957 → content ✅ | **Rotate180** (0.41 / 0.89) ✅ |
| invoice 150 dpi PNG (straight) | 0.05 ✅ | 0.98721 → content ✅ | upright (0.98 / 0.38) ✅ |
| patch sheet T (0.3° generated) | 0.25 ✅ | 0.98730 → content ✅ | upright |
| sparse page ("Page 2 of 2" only) | 0.00 | 0.99979 → **blank ⚠** | upright (0.99 / 0.41, 1 line) |

- **Timings:** skew 40–170 ms, white ratio 20–70 ms, orientation **~2.3 s** per text page (~1 s on a blank page:
  detection only). The first version sampled 12 full-width lines and took ~4.1 s.
- **Original unchanged:** SHA-256 of the original TIFF is identical before and after `PageAnalyzer` and after exporting with
  rotation + deskew + crop. The upside-down page exported with `Rotate180` is **pixel-identical** to the upright note.
  A 3° page exported with `DeskewAngle = 3.0` measures straight (within ±0.15°).

**Findings / follow-ups**
- **Sparse pages count as blank.** White ratio alone can't tell a page with one short line ("Page 2 of 2", a lone
  signature) from a blank one: 0.99979 vs 0.99980 for the stapled blank. For M3 blank-page separation, add a second
  check. The orientation pass already shows it: the sparse page has one text line read at 0.99 confidence, the blank
  pages have none. So "white ratio ≥ threshold **and** no confident text line" is a cheap fix.
- **Orientation cost:** at ~2.3 s it's nearly a full OCR pass. In the real pipeline (M2/M3), take the upright score from
  the page's normal OCR and only run the 180° check when that confidence is low.
- **90°/270° pages** (landscape sheets fed sideways) aren't detected yet; the same comparison works with quarter turns
  if needed.
- **Crop then deskew:** `Page.Crop` is in original pixels, so export crops first and then deskews, which can clip the
  corners of a tight crop. If M2's crop tool works on the deskewed view, store the crop in deskewed coordinates instead.
- Export writes via OpenCV (8-bit). Writing G4 output is Task 1.5 (LibTiff).
- `Page.DeskewAngle` needs a column in the Task 1.5 EF model.
- The image-processor tests use OpenCvSharp directly to compare exported pixels. The layering rule (third-party
  imaging only in Infrastructure) is enforced for the `src/` projects; the test project is outside it.

## Task 1.5: SQLite + PDF-OCR / multi-page TIFF export, 2026-10-28

**Setup**
- **SQLite (EF Core 10, `IProfiler.Data`):** `CaptureDbContext` with `Batch → Document → Page` and the `InitialCreate`
  migration. `EfBatchRepository : IBatchRepository` (Core) uses one short-lived context per call. Stored per page:
  `ImagePath`, `Rotation` (degrees: 0/90/180/270), `DeskewAngle`, `Dpi`, `Crop_X/Y/Width/Height` (complex type), `Order`,
  `PatchCode`. **No image data**: the schema has no BLOB column. `AddCaptureDatabase(paths)` is registered in `AppHost`;
  `dotnet-ef` is a repo-local tool (`dotnet tool restore`). A test fails if the model changes without a migration.
- **One mapping for export:** `ExportGeometry` (Core) maps original pixels ↔ export pixels for crop → deskew → quarter
  turn. `IImageProcessor.RenderForExportAsync` now returns the geometry it applied, so overlays use the same maths as
  the pixels (tested against the OpenCV render for all 4 rotations × 3 deskew angles, to within 1 px). It has an inverse
  for the M2 viewer's crop handles.
- **Real DPI (review follow-up):** `Page.Dpi` (from the scan request) if set, else the TIFF's `XResolution` tag via
  LibTiff, else the old A4-width estimate (JPEG/PNG for now). Used by the PDF page size, the TIFF tags, the white-ratio
  speck size and the patch-code bar sizes.
- **`PdfSharpAssembler`** (PDFsharp 6.2.4, MIT): each page rendered through `RenderForExportAsync` to a PNG and placed
  at its real size (300 dpi A4 → 595 × 842 pt). OCR words go into a separate content stream with **text render mode 3**
  (invisible). Each word is stretched to its box (glyph cell from ascent to descent = box height), and a stretched space
  fills the gap to the next word so readers get real spaces. PDFsharp has no render-mode API, so `3 Tr` is inserted
  after each `BT` of that stream.
- **`LibTiffAssembler`** (LibTiff.NET 2.4.660, BSD): each page rendered to a single-page TIFF and copied in. Bilevel →
  1-bit **CCITT G4**, grey/colour → LZW with predictor. Every page is tagged with its DPI, `PageNumber` and `SubFileType=Page`.
- **Samples:** `tools/make-pdf-samples.py` generates an A4 page with known word positions:
  - a letterhead with wide letter spacing, "SIMEN UTARA SDN BHD" (0.35 em)
  - very wide spacing, "TERIMA KASIH" (0.8 em, so letter gaps are half a word gap)
  - "TOTAL" at 30 pt with "RM 12,345.60" at 11 pt on the same line
  - an address, invoice number, date and item line

  It comes in three variants: upright G4 300 dpi; skewed 1.5°; upside down as 8-bit grey with a 200 dpi tag.
- **Spike:** `IProfiler.Spike export <TestData> <out>` analyses 4 pages (deskew + orientation), stores the batch, reads it
  back through a new context and exports from the **stored** metadata only. **Checker:**
  `tools/check-searchable-pdf.py <out>/manifest.json` searches 8 phrases + all 40 words per page in **two real readers**,
  MuPDF and **PDFium** (the engine in Chrome/Edge). A hit passes if it covers the true words horizontally (≥ 0.8 overlap,
  or both ends within 1.5 pt), the true text's centre line is inside it, and it is ≤ 3× the ink height. Highlights span
  the font's ascent to descent, so they are taller than the tight ink boxes of the truth.

**Results** (dev PC, Release, `export4` run)

| Page (stored metadata) | PDF size | Phrases (MuPDF + PDFium) | Words MuPDF / PDFium | Centre offset |
|---|---|---|---|---|
| skewed 1.5° G4, deskew **1.50** | 595.4 × 841.7 pt | **8/8** | 40/40 / 40/40 | 0.2–1.6 pt |
| upright G4, crop (150,200,2300,3200), deskew 0.05 | 552.0 × 768.0 pt | **8/8** | 40/40 / 40/40 | 0.2–1.9 pt |

| delivery note G4, deskew 0.50 | 595.2 × 841.9 pt | (no truth) | — | — |

- **24/24 phrase searches pass in both readers**, including "SIMEN UTARA", "SIMEN UTARA SDN BHD", "TERIMA KASIH" and the
  mixed-size "TOTAL RM 12,345.60". The one word miss is the lone **"x"** on the 200 dpi page. It is in the right place
  (0.94 overlap, 1.3 pt off), but its highlight is 3.06× its x-height ink, just over the limit. PDFium's extracted text

- **Invisible:** every text span on every page is render mode 3 (MuPDF texttrace type 3). A PDFium render of page 1

- **Multi-page TIFF:** 4 pages in order: 2481×3507 G4 300 dpi, 2300×3200 G4 300 dpi (cropped), 1654×2338 grey LZW

- **DB holds only metadata:** 48 KB file for 4 pages; tables `Batches`, `Documents`, `Pages` (+ EF history); **0 BLOB

- **Timings:** analysis 11.4 s for 4 pages (orientation 2.4–3.3 s + skew 0.13–0.18 s each); SQLite 1.9 s, which is

**What failed first, and the fixes** (same pages, baseline run → final run)

| Problem (baseline) | Cause | Fix | After |
|---|---|---|---|
| "TERIMA KASIH" not found on any page (0/3 in both readers) | Paddle's English recogniser mangles wide letter spacing: it reads `TERIMAKASIH` (word break lost), `T E R I M A` + `K A S I H` (a space between every letter), or `K ASIH` | Ink-gap word boxes now handle letter-spaced lines. **Findings / follow-ups**
- ⚠ **PDFsharp went AGPL.** 6.5.0 (14 Oct 2026) is AGPL-3.0 with a licence-key check (`PdfSharpLicenseException`
  without a key). **6.2.4 (Jan 2026) is the last MIT release.** It is pinned, and a test fails on any 6.3+ version.
  MIT 6.2.4 gets no more fixes, so the PDF library is now a **team-lead decision before M4** (R12): stay on 6.2.4,
  QuestPDF (licence check), or PdfPig (Apache-2.0) / own PDF writer for image + text-layer output. PDFsharp 6.2.4 also
  asks for `System.Security.Cryptography.Pkcs` 8.0.1 (advisories), pinned to 10.0.14.
- **Where OCR runs (M2/M3 design):** for text layers and highlights, OCR the deskewed/upright render, not the original,
  and store the boxes in original pixels (`MapBoxes`). They then stay valid if the user changes the crop later. A user
  rotation change after OCR breaks the "text reads upright in the export" assumption, so re-OCR or re-map then.
- **Image size in the PDF:** pages go in as PNG (lossless; bilevel pages as 8-bit grey Flate). Fine for B/W (≈ 50 KB per
  A4 page here), but colour 300 dpi pages will be large. M4: CCITT G4 for bilevel and JPEG (quality setting) for colour
  photos, which needs a PDF writer that accepts pre-encoded images.
- **Text-layer font:** Arial from Windows fonts (`UseWindowsFontsUnderWindows`), subset-embedded, Unicode ToUnicode
  map. Only its metrics matter.
- **"x"-height words:** highlights span the whole glyph cell, so one-letter lowercase words look tall. That is cosmetic.
- **JPEG/PNG DPI** is still estimated from the A4 width (JFIF/pHYs not read yet); TIFF is what scanners produce.
- **Startup migration:** `MigrateCaptureDatabaseAsync` isn't called at app start yet (nothing uses the DB). Add it in M2
  and re-test the installer in Sandbox: `e_sqlite3.dll` ships in the publish output.

**Recommendation on D6: GO, keep the open-source stack.** Conditional on Task 1.1.
- Every capability except scan acquisition works end to end, offline, from a self-contained install.
- It runs on permissive libraries (Apache/MIT/BSD) at acceptable speed on a mid-range CPU. Speed is managed by the
  background analysis queue, not by a different library.
- The problems found are packaging and licensing (VC++ runtime, PDFsharp licence, code signing, Media Foundation).
  Each has a known fix. None is a capability gap that a paid all-in-one SDK would close.
- A paid SDK would replace Paddle/OpenCV/ZXing/PDFsharp, which already work. It would not remove the need for code
  signing or a 32-bit TWAIN path.

**What would reopen D6 (per section B):**
- Task 1.1 shows the AD7100, or typical client-site scanners, can't be driven reliably through NAPS2.Sdk or NTwain +
  our own 32-bit worker.
- The team lead rejects both LGPL (NAPS2) and building our own worker.

Real-scan OCR accuracy (R6) also feeds this decision, and is measured in Task 1.1.
